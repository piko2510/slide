# 台本｜スキル編：スキルとはなにか（全10枚）

AIエージェント入門の2本目です。スキルとは、モデルを変えずに「頼み方」を決める手順書であることを説明します。
後半（4〜6枚目）はエンジニア向けに、スキルの実物の姿（ファイル構成と、SKILL.mdに何を書くか）を示します。
掲載文言・台本はこのファイルが正本です。デザインは同じフォルダのdesign.mdが正本です。

## 1｜スキルとはなにか

**この一枚：** 表紙。スキルはモデルへの頼み方を書いた手順書である、という主題を置く。

**掲載文言：**

> スキルとはなにか
>
> モデルを変えずに、頼み方を決める手順書の話
>
> 頼む人：仕事を頼む
> スキル：頼み方の手順書
> ✓ 探すもの　✓ 返す形
> ✓ 分からないとき
> モデル：仕事をする
>
> この資料は、スキルの説明だけをします。モデルの説明は、前の資料です。

**図・配置：** 全面ティールの表紙。左から右への流れ（頼む人 → スキル → モデル）で、中央のスキルは白い吹き出しで示す。

**話す内容：**

この資料では「スキルとはなにか」を説明します。スキルは、モデルそのものではなく、モデルへの頼み方を書いた手順書です。この後のページで、モデルとの違い、作るときの注意、良い書き方を順に説明します。

**技術注記：**

表紙の図は左から右への流れです。頼む人がスキル（手順書）を通してモデルに仕事を渡します。表紙はモデル編と同じ全面ティールの地で、中央のスキルは白い吹き出しで示しています。図形はすべてPowerPointの図形とコネクタで、後から編集できます。

## 2｜スキルは、モデルを変えずに「頼み方」を決める手順書だ

**この一枚：** 定義。スキルはレシピや作業マニュアルと同じで、頼み方を先に書いておくもの。

**掲載文言：**

> スキルは、モデルを変えずに「頼み方」を決める手順書だ
>
> たとえば、料理のレシピや
> 仕事の手順書のようなもの。
> 書いてあるから、頼むたびに
> 説明し直さなくていい。
> 友達そのものではなく、
> 友達への頼み方のメモだよ。
>
> 手順書に書くこと
> - 探すものは何か
> - 返す形はどうするか
> - 分からないとき、どう言うか
>
> レシピや作業マニュアルと同じです。同じ頼み方をすれば、毎回同じ進め方になります。

**図・配置：** 左にたとえ話の本文、右に主色のベタ面のパネルを置き、その中に「手順書に書くこと」の3項目を白い吹き出しで示す。

**話す内容：**

スキルはレシピや作業マニュアルのようなものです。中身は新しい能力ではなく、頼み方の決めごとです。探すもの、返す形、分からないときの言い方を先に書いておくことで、頼むたびに説明し直さなくてよくなります。

**技術注記：**

モデル自体は変更しません。スキルはモデルの外側にある指示の集まりであり、モデルのできること・できないことの範囲は変わりません。右の3項目は、この後のページで繰り返し出てくる手順書の中身です。

## 3｜モデルとスキルは、役割が違う

**この一枚：** 役割の対比。できる・できないはモデルで決まり、頼み方はスキルで決まる。手順書を書いても、できないことはできるようにならない。

**掲載文言：**

> モデルとスキルは、役割が違う
>
> モデル：友達そのもの
> できることと、できないことが
> ここで決まる
>
> ≠
>
> スキル：頼み方の手順書
> 頼み方と、進め方が
> ここで決まる
>
> スキルを書いても、できないことが、できるようにはなりません。

**図・配置：** 左右の対比。モデル側は輪郭だけのパネル、スキル側は主色のベタ面で主役にする。間に「≠」を置く。下段の注意は、オレンジの「！」と組にして置く（オレンジはこの注意だけ）。

**話す内容：**

モデルとスキルは別のものです。できる・できないはモデルで決まり、頼み方はスキルで決まります。ここを取り違えると、「手順書を書けば何でもできるようになる」という誤解が生まれます。

**技術注記：**

能力の上限はモデル側にあります。スキルはその範囲内で、得意な使い方を引き出すためのものです。できないことが残るのは異常ではなく、前提です。下段の注意だけ、アクセントのオレンジを使っています。

## 4｜スキルは、フォルダ1つでできている

**この一枚：** エンジニア向けの実物の姿（1）。スキルはフォルダ1つで、中核は必須のSKILL.md。

**掲載文言：**

> スキルは、フォルダ1つでできている
>
> my-skill/（フォルダ名 = name）
> ├── SKILL.md：必須。中核の指示書
> ├── scripts/：実行するコード
> ├── references/：参照資料
> └── assets/：テンプレート・素材
>
> 必須は SKILL.md だけ
> 残りは、必要に応じて同梱します。
> scripts/ は決まった処理をコードで実行させるため、references/ は本文に書ききれない資料、assets/ は出力に使う雛形や素材です。
>
> スキル1つ = フォルダ1つ。配布も共有も、フォルダごとに行います。

**図・配置：** 左にフォルダツリーを大きく示し、各項目の右に役割を対応させる。右に必須と任意の区別と、各フォルダの用途の説明を置く。ツリーの文字は主要部分として大きく保つ。

**話す内容：**

ここからは、スキルの実物の姿です。スキルはフォルダ1つでできています。中核は SKILL.md という1ファイルで、これは必須です。必要に応じて、実行するコードを置く scripts、参照資料の references、テンプレートや素材の assets を同じフォルダに同梱します。

**技術注記：**

Agent Skills の公開仕様に基づく構成です。フォルダ名はフロントマターの name と一致させます。scripts / references / assets はいずれも任意で、最小構成は SKILL.md のみです。出典: https://developers.cloudflare.com/agents/concepts/agent-skills/

## 5｜SKILL.md は、スキル1つの中身を書いたファイルです

**この一枚：** エンジニア向けの実物の姿（2）。SKILL.md の簡単な解説。中身は頭のフロントマターと、本文の Markdown の2つに分かれる。

**掲載文言：**

> SKILL.md は、スキル1つの中身を書いたファイルです
>
> ---
> name: log-triage
> description: ログを検索・仕分けする。
> 　　ログ調査を頼まれたときに使う。
> ---
> （以下、本文を Markdown で書く）
> 手順やルールを、ここに書きます。
>
> 頭 — フロントマター
> name と description の2つを書きます。description は「いつ使うか」の看板で、モデルはこれを見て使うかどうかを決めます。
> 本文 — Markdown
> 手順やルールなど、仕事の進め方を書く本体です。詳しくは次のページです。
>
> モデルは、使うと決めたときに、この1ファイルを開いて読みます

**図・配置：** 左に SKILL.md の実例をコードとして大きく示す（フロントマターと、本文の書き出し）。右に「頭 — フロントマター」「本文 — Markdown」の2段の説明を対応させる。下部に、モデルが使うと決めたときに開く、という一行を吹き出しで置く。

**話す内容：**

フォルダの中核が SKILL.md です。これは Markdown ファイル1つで、中身は大きく2つに分かれます。頭のフロントマターには name と description を書き、特に description が「いつ使うか」の看板になります。モデルはまずこの看板を見て使うかどうかを決め、使うと決めたときに本文を開いて読みます。本文には手順やルールなど、仕事の進め方そのものを書きます。本文に何を書くかは、次のページで説明します。

**技術注記：**

公開仕様では SKILL.md が必須ファイルで、YAMLフロントマターの name と description が必須フィールドです。name は最大64文字で小文字・数字・ハイフン、フォルダ名と一致させます。description は最大1,024文字です。読み込みは段階的で、開始時は name と description のみ、タスクが一致したときに本文（Markdown）が読み込まれます。出典: https://developers.cloudflare.com/agents/concepts/agent-skills/

## 6｜本文には、手順とルールと、入出力の形を書く

**この一枚：** エンジニア向けの実物の姿（3）。フロントマターの下の本文に書く4項目と、段階的開示。

**掲載文言：**

> 本文には、手順とルールと、入出力の形を書く
>
> 手順：仕事の進め方を、順番に書く
> 守るべきルール：してよいこと・しないことを明記する
> 入出力の形：何を受け取り、何を返すかを決める
> 例外の扱い：分からないときは「分からない」と返す
>
> 詳細な資料は references/ に分け、必要なときに読みに行く作りにします。
> 全部を最初から読み込ませません（段階的開示）。

**図・配置：** 4項目を、項目名と説明の対応表で示す。項目の順序は吹き出しの並び順そのもので表す。下部に段階的開示の補足を置く。

**話す内容：**

フロントマターの下の本文には、仕事の中身を書きます。手順、守るべきルール、入出力の形、そして例外の扱いです。分からないときにどう返すかまで書いておくのが要点です。詳細な資料は references に分けておき、必要なときに読みに行く作りにします。

**技術注記：**

本文は Markdown で書きます。公開仕様は本文の形式に細かい規則を置いておらず、推奨は本文を絞り、詳細は references/ へ分けることです。読み込みの3段階（カタログ、本文、リソース）が段階的開示です。出典: https://developers.cloudflare.com/agents/concepts/agent-skills/

## 7｜できないことは、無理にお願いしない

**この一枚：** 短所の扱い。短所に当たらないように仕事を分けて渡す。

**掲載文言：**

> できないことは、無理にお願いしない
>
> 悪い頼み方　「原因を特定して、直して」
>
> 短所に当たらないように、仕事を分けて渡します。
>
> 解析する：コードへ。決まった処理は機械的に
> 探す・仕分ける：モデルへ。得意な仕事だけを渡す
> 最終判断：人・強いモデルへ。責任がいる判断はこちら

**図・配置：** 上部に悪い頼み方をオレンジの帯で大きく示し、主役にする。下部は渡す先の3つを役割の重さで幅を変えて並べ、モデルへの列を広く主色にする。

**話す内容：**

芯は短所の扱いです。短所を隠すのではなく、短所に当たらないように仕事を分けます。解析はコードへ、最終判断は人や強いモデルへ回し、モデルには探す・仕分けるといった得意な仕事だけを残します。

**技術注記：**

「原因を特定して直して」は、推論の連鎖と責任ある判断を含むため、このモデルの短所に当たります。仕事の分解が、スキル設計の中心作業です。オレンジは悪い頼み方の側だけに使っています。

## 8｜長所を伸ばす書き方をすると、得意な仕事が返ってくる

**この一枚：** 長所を伸ばす書き方の4点と、その例。

**掲載文言：**

> 長所を伸ばす書き方をすると、得意な仕事が返ってくる
>
> 探すものを書く：例：エラー時刻と、該当する行
> 返す形を書く：例：時刻の順に並べて渡す
> 分からないときの言い方を書く：例：「分からない」と書く
> 仕事は1回に1つだけにする：例：探す、と仕分ける、は分ける

**図・配置：** 4項目を、書き方と例の対応表で示す。順序は吹き出しの並び順で表す。

**話す内容：**

長所を伸ばす書き方は4つです。探すものを書く、返す形を書く、分からないときの言い方を書く、仕事は1回に1つだけにする。この4つがそろうと、モデルは得意な仕事に集中できます。

**技術注記：**

「分からない」と言わせる指定が特に重要です。分からないものを、知っているものと間違えて返す失敗を防ぎます。例はログ調査を想定しています。このページは吹き出しの並び順そのもので手順の順序を表しています。

## 9｜頼み方を具体的にすると、答えが使えるものになる

**この一枚：** 山場。あいまいな頼み方と具体的な頼み方の対比。

**掲載文言：**

> 頼み方を具体的にすると、答えが使えるものになる
>
> あいまいな頼み方
> 「ログを見ておいて」
> 何を探すのかが決まらず、
> 答えが毎回ぶれます
>
> ✓ 具体的な頼み方
> 「エラー時刻と該当行を抜いて、
> 重さで仕分けて。
> 分からないものは
> 『分からない』と書いて」
> 探すものと返す形が、決まっている
>
> 書くのはこの4点だけです。探すもの、返す形、分からないときの言い方、仕事は1つ。

**図・配置：** 左右の対比。左のあいまいな頼み方は輪郭だけのパネルに小さく置き、オレンジの「！」を添える。右の具体的な頼み方は主色の濃いベタ面で一番大きく作る。この資料で最も強く作る。

**話す内容：**

同じモデルでも、頼み方で答えは変わります。左の「ログを見ておいて」では何を探すのか決まらず、答えがぶれます。右のように探すもの・返す形・分からないときの言い方まで書くと、そのまま使える答えが返ります。このページが、この資料の山場です。

**技術注記：**

右の頼み方は、検索・抽出・仕分けというモデルの長所だけに仕事を絞った例です。原因の特定や修正は含めていません。山場なので、右の面を主色の濃い面で一番大きくしています。

## 10｜まとめ

**この一枚：** まとめ（静かに）。スキルは魔法ではなく、得意が生きる頼み方を書いて残すもの。

**掲載文言：**

> スキル
>
> スキルは魔法ではない。
> 得意が生きる頼み方を、書いて残すものだ。
>
> 短所は、隠さない：当たらないように、仕事を分ける
> 長所は、伸ばす：探すもの・返す形・分からないときの言い方を書く
> 頼み方は、残す：書いて残せば、他の人も同じように頼める
>
> できないことは頼まない。得意な頼み方をする。それだけで、友達はちゃんと役に立つ。

**図・配置：** 淡い色と余白だけで静かに閉じる。上部に吹き出しで「スキル」と置き、中央にまとめの文、その下に3行の対応を置く。

**話す内容：**

まとめです。スキルは魔法ではなく、得意が生きる頼み方を書いて残すものです。短所は隠さず仕事を分け、長所は書き方で伸ばし、頼み方を残すことで他の人も再現できます。

**技術注記：**

再現性が最後の要点です。手順書として残ることで、頼み方の品質が個人の工夫から、共有できる形に変わります。まとめは静かに、淡い色と余白だけで閉じています。
