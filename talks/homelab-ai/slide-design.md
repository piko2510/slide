# わしの家のAI環境

スライド設計書（2026年9月25日）

副題：AIに任せたくて、作って、壊して、今こうなった

## 発表の目的

社内のエンジニアへ、自宅のAI環境で何をしているかを最初に見せる。自宅Proxmox上の作業環境と情報基盤を、Codex、クラウドのAIモデル、GitHubとどう組み合わせているかを説明する。普段の開発依頼を一件の到達点まで任せたいことと、過去の事情を毎回説明し直す負担を減らしたいことを、設計の動機として伝える。

起（01〜05）は家の構成と、本人がAIへ渡したい依頼と受け取りたい結果。承（06〜07）は人間が中継していた頃と、旧Harnessを管理する負担。転（08）は独自Harnessの撤去と組み直し。結（09〜13）では、同じ説明用の依頼を現在の環境で入力から受入まで追い、残る課題に戻る。Context DBとJevはこの依頼の受け渡しを支える要素として扱い、独立した技術紹介にはしない。「何を自分で持たないか」は結論での学びに置く。これは本人の運用経験を話す発表であり、一般的なモデル性能の比較や完全自律の成功報告ではない。

本編10分、質疑5分。開催日は未定。ページは13枚とし、次の配分で合計600秒にする。

| 範囲 | 内容 | 時間 |

| 06〜07 | 承：人間中継と旧Harnessの肥大化 | 90秒 |
| 08 | 転：独自Harnessの撤去と組み直し | 45秒 |
| 09〜13 | 結：現在の依頼の流れと課題 | 225秒 |

### 01｜わしの家のAI環境

**役割：** 自宅で開発環境と情報基盤を作り、AIと組み合わせて使っている本人の話として導入する。\
**時間：** 20秒

**掲載文言**

> わしの家のAI環境\
> AIに任せたくて、作って、壊して、今こうなった

**図と配置：** タイトルと副題だけを大きく置き、余白を残す。環境の構成は次ページで説明する。

**口頭説明：** 「家にAIモデルを置いて推論している話」ではなく、自宅の作業環境と情報基盤を使い、クラウドのモデルへ仕事を任せるために試したことを話す。作った仕組みを壊した経緯も隠さない。

**次への接続：** 「まず、今どこに何を置いているかから見せます。」

### 02｜家に置いているものと、クラウドに任せるもの

**役割：** 今の環境を、この1枚で大づかみに理解できるようにする。\
**時間：** 60秒

**掲載文言**

> 自宅：Proxmox上のVMに、作業環境と情報基盤\
> クラウド：CodexからAIモデルを利用\
> GitHub：Issue、PR、review、CIなど開発の状態

図の下に「モデルの推論はクラウド。自宅VMは作業と情報を支える」。

**図と配置：** 左半分を「自宅」枠とし、その中にProxmox、その上のVM群として「作業環境」「Context DBなどの情報基盤」を並べる。右上に「クラウドのAIモデル」、右下に「GitHub」を置く。自宅の作業環境内にCodexを示し、そこからモデル利用の線を引く。GitHubへの線はIssueやPRなど開発状態のやり取りとして示す。人間は図の左端に置き、作業環境へ依頼する線を引く。機器スペック、VM番号、IP、通信方式は描かない。

**口頭説明：** Proxmox上のVMは、AIの作業場所と、必要な事情を残す情報基盤を受け持つ。推論はCodexを通じてクラウドのモデルを使う。Gitは変更履歴を持ち、GitHubはIssue、PR、review、CIの開発状態を持つ。図は責務と主な関係の概略で、全通信経路を表すものではない。

**次への接続：** 「これを置いているのは、普段の開発依頼でやりたいことがあるからです。」

### 03｜この環境でやりたい日常の仕事

**役割：** 構成の目的を、日常の二つの負担に結び付ける。\
**時間：** 40秒

**掲載文言**

> 開発の依頼を、一件の到達点まで任せたい\
> 前に決めた理由や制約を、毎回説明し直したくない

小さく「目標：通常の調査、実装、検証、局所修正をつなぐ」「人間が必要な判断は残す」。

**図と配置：** 二つの目的を左右に大きく対比し、それぞれの左端に青い縦線を置く。下に人間が決めることを残す短い一文を添える。

**口頭説明：** 目指しているのは、回答を一つ得ることより、指定した到達点まで仕事を進めてもらうこと。必要な人間判断は戻してもらう。ここでいう二つは設計上の狙いであり、毎日すべて成功しているという実績ではない。

**次への接続：** 「そのために、まず自分がどんな依頼を渡したいかを考えます。」

### 04｜自分がAIに渡したい依頼

**役割：** 使い手の立場から、目的、範囲、終わり方を一件の依頼として示す。\
**時間：** 60秒

**掲載文言**

> 「公開資料のリンク切れを直して、確認結果まで返して」

下部に「目的：読者が資料を開ける」「範囲：指定した公開資料」「終わり方：修正箇所と確認結果を返す」。注記：「以降も使う説明用の例。実行記録ではない」。

**図と配置：** 上に依頼文を大きく置き、下に「目的」「範囲」「終わり方」の三枠を横に並べる。担当者やモデルの箱、内部の処理順はまだ描かない。

**口頭説明：** 自分が渡したいのは細かな工程表ではなく、何を直したいか、どこまで触れてよいか、何が返れば終われるか。リンク修正は流れを説明するための公開可能な題材で、実際の成功例ではない。依頼先が必要な資料を調べ、許可の範囲で進めることを期待している。

**次への接続：** 「では、何が返ってくれば、自分は途中の段取りを引き受けずに済むか。」

### 05｜自分に返ってきてほしいもの

**役割：** 本人が受け取りたい結果と、人間の判断が必要な場合を示す。\
**時間：** 60秒

**掲載文言**

> 直した箇所／どう確かめたか／まだ確かめられないこと

下部に「新しい権限や範囲が要るなら、その判断だけ戻してほしい」。

**図と配置：** 「直した箇所」「どう確かめたか」「残る未確認」の三つの受取欄を横に並べる。下に人間へ戻す「新権限・範囲・重要判断」の帯を置く。親Astraと各担当の配役図は置かない。

**口頭説明：** 自分が毎回調査結果を読み替えて次の担当へ指示し、再検証を促す状態を減らしたい。修正できたと言うだけでなく、どの資料を直し、何で確認し、残る不確かさが何かを受け取りたい。一方、依頼した範囲を越える操作や結果を大きく変える判断は、自分が引き受ける。ここで示すのは目指す受け渡しであり、常に自動で完了するという実績ではない。

**次への接続：** 「この受け渡しをしたくて、最初は自分で段取りをつないでいました。」

### 06｜最初は、自分がAIの段取り係だった

**役割：** 独自Harnessを作った動機を、本人の作業から説明する。\
**時間：** 45秒

**掲載文言**

> 事情を説明する → 指示を中継する → 結果を読む → 止まれば再開させる\
> AIへ任せるための段取りを、自分が回していた。

**図と配置：** 横一列の四工程それぞれの上に「自分」を置く。工程間を結び、最後から最初へ戻る線で段取りの反復を示す。

**口頭説明：** 単発の回答は得られても、仕事が次の工程へ進むたびに自分が中継していた。失敗後の再開も同じ。人間が毎回つなぐ仕事を減らすため、旧Harnessへ進行管理を移そうとした。

**次への接続：** 「移してみると、事故を防ぐ仕組みが一つずつ増えました。」

### 07｜事故を防ぐたびに、管理するものが増えた

**役割：** 旧Harnessの機構を、防ぎたかった事故と組にして見せる。\
**時間：** 45秒

**掲載文言**

| 防ぎたかったこと | 足した仕組み |
|---|---|
| 二重実行 | claim / lease |
| 許可範囲を越える操作 | Authority / gate |
| 中断後の誤った再開 | checkpoint / receipt |
| 古い変更のまま受け入れる | 対象headの照合 |

下部：「仕事を管理する仕組みも、管理する必要が出た」。

**図と配置：** 左に防ぎたかった事故、右に足した仕組みを四行で対応させる。下に「管理の仕組みも管理する必要が出た」と置く。対応表を因果の矢印で飾らない。

**口頭説明：** 追加の一つ一つには理由があった。だがGitやGitHubの状態に加えて独自の作業状態も持つと、両者の対応を保つ仕事が増える。必要な安全確認そのものを否定する話ではない。

**次への接続：** 「そこで、状態を自作で持ち続ける設計をやめました。」

### 08｜独自Harnessを撤去して、標準機能へ戻した

**役割：** 独自Harnessの撤去と現在の組み直しを、話の転換点として示す。\
**時間：** 45秒

**掲載文言**

> 300 files changed / 375,900 deletions / 629 additions

| 責任 | 現在の置き場所 |
|---|---|
| 実行 | Codex |
| branch、commit、diff、worktree | Git |
| Issue、PR、review、CI、merge状態 | GitHub |
| 必要な接続、入力加工、安全境界 | 自作部分に残す |

注記：「旧Harness撤去commitのGitHub差分。手書きLOCや効果の測定値ではない」。

**図と配置：** 上に撤去差分の数値を単位付きで置く。下は左に旧Harness、右に標準機能と残した自作部分を一つの大きな枠で示し、責務の移動を線で結ぶ。差分の注記に、手書きLOCや効果の値ではないことを記す。

**口頭説明：** 実行ループや開発状態は標準の仕組みに戻した。外部Providerへの接続、入力加工、必要な安全境界まで消したわけではない。GitHub差分のdeletionsは生成物なども含み得るため、手書きコードの削減量や生産性改善としては使わない。撤去後も規則の肥大化やAstraへ仕事を集めすぎる課題があり、現在の役割分担を調整してきた。

**次への接続：** 「組み直した今の環境で、さっきの依頼がどう進むかを見ます。」

### 09｜作り直した今のハーネスの全体像

**役割：** 4枚目の説明用の依頼が、現在の環境でどう進むかを一枚で見せる。

**時間：** 45秒

**掲載文言**

> 公開資料のリンク切れを直し、確認結果を返す
>
> 依頼 → 必要な文脈 → 担当へ委任 → 修正と検証 → 結果と根拠 → 親の受入

注記：「説明用の流れ。実際の実行記録ではない」。

**図と配置：** 上部に依頼文を置き、中央は「入力を整える」「担当が実行」「根拠で受入」の三列にまとめる。依頼の整理、必要な文脈、担当への直接委任、修正と検証、結果と根拠、親の受入を各列の中で追えるようにする。Context DBから必要な文脈への入力線は下から上へ向ける。Jevを必須の直列工程として置かない。

**口頭説明：** 親Astraは現在の依頼を整理し、必要なら関連する事情を参照する。選んだ担当へ到達点までの仕事を直接渡し、担当は修正と検証を行う。親が結果と根拠を見て受け入れるか判断する。各箱は説明上の要点であり、毎回同じ資料取得や工程が必須という意味ではない。

**次への接続：** 「まず、担当へ何を渡せば、意図と制約が伝わるかです。」

### 10｜担当に、何を渡すか

**役割：** 現在の依頼と過去の事情を区別し、受け渡しの中でContext DBとJevが担う部分を示す。

**時間：** 40秒

**掲載文言**

> 現在の依頼：目的、範囲、必須指示、権限、受入条件
>
> 関連する事情：理由、制約、時点、出典、訂正

下部：「参考資料だけ、必要な受け渡し箇所で限定選別」。

**図と配置：** 左上に現在の必須情報、左下にContext DBの参考資料を置き、右の「担当への入力」へ二つのレーンで届ける。必須情報は直接つなぎ、参考資料だけ途中の小さなJev補助枠を通す。候補化と入力組立はコードで行う。Jevの結果が未評価なら参考情報と不確実性を残す。

**口頭説明：** リンク先を選んだ理由や公開範囲の制約が記録されていれば、関係を確かめて添える。これは説明上の想定で、実在記録の引用ではない。過去の記録は現在の許可ではない。Jevは参考資料だけを既存の受け渡し箇所で選別補助する。誤判定や材料不足、fallbackでの制約欠落を経験したため、必須情報は通し、不確実な資料を不要と決めない。

**次への接続：** 「目的と事情を渡したあと、担当にはどこまで進めてほしいか。」

### 11｜任せた担当が、どこまで進めるか

**役割：** 担当が一件を進める範囲と、判断を戻す境界を示す。

**時間：** 40秒

**掲載文言**

> リンクを確認 → 許可された範囲で修正 → 再検証
>
> 局所的な失敗は、原因を確かめて同じ担当が続ける。

下部：「新しい権限、範囲、重要な判断は親へ返し、必要なら人間へ」。

**図と配置：** 「調べる」「修正する」「検証する」の三枠を横に並べ、検証で見つかった局所的な誤りから修正へ戻る線を下側に引く。範囲外の判断は別の帯に置く。Sol、Luna、Grokなどの名前は口頭で必要な範囲だけ触れ、能力順位の図にしない。

**口頭説明：** この例なら、担当はリンクを調べ、許可範囲で修正し、再確認する。局所的な失敗は原因を見て同じ担当が直し、検証する。親は調査や検証をSol、照合しやすい仕事をLuna、通常のコード実装をGrokなどへ直接割り当てる。権限や範囲の拡張は担当だけで決めない。

**次への接続：** 「作業が進んだだけでは、依頼が終わったとは言えません。」

### 12｜何を見て、終わったと判断するか

**役割：** 結果の報告から親の受入までを、開発状態の正本とともに示す。

**時間：** 40秒

**掲載文言**

> 直した箇所／確認した結果／残る未確認
>
> 親Astraが依頼の到達点と根拠を照合する。

下部：「Git＝変更の正本／GitHub＝PR、review、CI、mergeなどの状態」。

**図と配置：** 左の「結果と根拠」、右の「依頼の到達点」の両方から中央の「親が照合」へ線を向ける。下段のGitとGitHubからも、参照する状態として中央へ線を引く。人間へ戻す「新権限、範囲、重要判断」は下の注記で分けて示す。

**口頭説明：** リンク修正の説明例なら、修正箇所とリンクの確認結果、未確認事項を受け取り、依頼した公開範囲と終了点に合うか親が判断する。必要なテストやreview、公開先の状態は、依頼の内容に応じて確認する。branch、commit、diffはGit、PRやmergeなどはGitHubの実状態を見る。担当の「完了しました」だけを受入の証拠にはしない。本人の新しい判断が必要な場合と、親が既存の委任範囲で受け入れる場合は分ける。

**次への接続：** 「この受け渡しが、自分の段取りをどこまで減らせるかが今の課題です。」

### 13｜今の自宅AI環境で目指していること

**役割：** 冒頭の環境図と本人の目的に戻り、工夫と未解決点をまとめる。

**時間：** 60秒

**掲載文言**

> 依頼と必要な判断は自分が持つ。通常の段取りは環境に任せたい。
>
> まだ調整中：規則の保守／文脈の選び方／担当の配役

注記：「Jevを含む全体効果は未測定」。下部：「学び：何を自分で持たないかも設計する」。

**図と配置：** 左に2枚目の自宅VM、Codex、Context DB、クラウドモデル、GitHubの環境図を縮小して再掲する。右に三つの未解決点と未測定の注記を置き、下に人間の中継を減らす目的を大きく置く。

**口頭説明：** 自宅VMは作業と情報の基盤、推論はクラウド、変更と開発状態はGitとGitHubが受け持つ。旧Harnessを撤去しても、規則の保守、どの事情を渡すか、誰にどこまで任せるかという調整は残った。Jevの正味効果も親子全体の時間、費用、往復、人間介入を含めては未測定。目指しているのは、本人が目的と必要な判断を持ちながら、説明や中継、再開の反復を減らすこと。そのために、自分で持たない状態や仕組みも選んでいる。

**次への接続：** 「ここから質疑に移ります。」

## 表現と公開の境界

- 自宅のProxmox上のVMは作業環境と情報基盤として描く。クラウドモデルをローカル推論しているように描かない。物理スペック、VM番号、IPなど未確認の構成値は足さない。
- 4枚目で示す開発依頼を9〜12枚目まで同じ説明用の例として追う。実行記録や成功実績に見せず、日常的な全自律完了や毎日の成功を断定しない。
- 撤去差分は当該commitのGitHub差分。手書きコード量、効果や生産性の数値として使わない。
- 規則の肥大化とモデル配役の試行錯誤は8枚目の口頭説明に留める。モデル配役は本人の運用方針であり、一般的な性能順位ではない。
- Jevは既存の受け渡し箇所で参考資料だけを扱う限定判断。必須指示、権限、受入条件は選別しない。操作許可、最終受入、システム全体の司令塔として描かない。全体効果は未測定と明記する。
- 実メール、非公開URL、内部IP、VM番号、認証情報、個人情報や顧客情報を載せない。
