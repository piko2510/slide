# わしの家のAI環境

スライド設計書 v5｜自宅環境と現在のCodexの実装・動作

副題：自宅サーバーとCodexで、AIに仕事を任せる

## 発表の目的

社内エンジニアに、自分が家で何を組み、どう使い、何に苦労しているかを紹介する。
目標は、本人が毎回事情説明・担当間の中継・作業の再開をしなくても、事情と意図を踏まえて、委任した到達点まで一件の仕事を進めてもらうこと。
PR作成、標準化、Skill作成それ自体を発表の目的にしない。

現在の自宅環境を最初に見せ、目的と人間の負担を挟み、現在のCodexの動作へ戻る。
独自ハーネスの開発史は扱わず、撤去は05の一枚で終える。
06以降は、モデル・ツール往復、担当分担、実ファイル、仕事の受入ループ、コンテキスト基盤、Jevを説明する。
08〜10は一般論ではなく、AGENTS.md、代表SkillのフォルダとSKILL.md、Hookの設定と呼出先を見せる。
SkillとHookは同じgithub-main-refreshの実装を追い、部品の関係が一続きで分かるようにする。
苦労は強い形容詞や開発史の枚数で増幅せず、現在の仕組みがどの負担への対処なのかを結び付ける。

**話す内容：**

共通の進め方は、リポジトリのAGENTS.mdに書いています。
画面は実際の規則を短くしたものです。
相談を変更許可にしない。
担当が返ってきても、受入条件が未達なら親が仕事を持ち続ける。
条件を満たしたら、勝手に改善を追加せず終える。
どれも、説明や再開の指示が私へ戻ってきたことへの対処です。

**台本外の技術注記：** 掲載例は要求・担当・完了に関する規則の短縮で、原文の見出し・全文の再現ではない。

元の範囲・権限内で続け、重要な未決事項、新たな費用・権限・範囲、安全境界、解消不能な外部阻害では本人へ戻す。

**台本外の技術注記：** Skill Creatorは作成支援であり、Skillの実行時に必ず通る仲介処理ではない。

### 10｜Hookで、決まったタイミングに処理を差し込む

**時間：55秒**

**この一枚：** Skillをモデルが選ぶ経路と、イベントから同じコードを直接呼ぶ経路を区別する。

**掲載文言：**

左は`.codex/hooks.json`の起動時部分の説明用短縮例。
「commandは短縮表示・実行用設定ではない」と明記する。

```json
{
  "hooks": {
    "SessionStart": [{
      "matcher": "^startup$",
      "hooks": [{"type": "command",
        "command": "…refresh_main.py",
        "timeout": 20}]
    }]
  }
}
```

右は、このリポジトリに定義されている二つの呼出し経路。

```text
SessionStart / startup
  → refresh_main.py
  → Git確認・fetch・安全条件で更新

PreToolUse / Agent
  → jev_preprocess_agent.py
  → assemble-recipient.mjs
  → 対象の入力を差し替え
```

下部の結論：

> Hookは呼出し契機。信頼確認・対象条件・失敗時の扱いがある。

**図・配置：** 左に短い設定、右に上下二つの処理の流れ。
SessionStartから09と同じPythonへつながることを強調する。
Jev側は入口だけを示し、候補選択の詳細は13へ送る。
JSON全文、全パス、SHA-256文字列、全例外分岐を画面へ詰め込まない。[^hooks]

**話す内容：**

Hookは、決まったイベントに処理を差し込む設定です。
このリポジトリでは、起動時のSessionStartから、先ほどの更新用Pythonを直接呼ぶ定義があります。
Skillの文章を経由して実行するのではなく、同じ処理本体を再利用しています。
もう一つが、Agentへ仕事を渡す直前の入力前処理です。
対象の構造化入力をassemblerへ渡し、結果が得られた時だけ入力を差し替えます。
Jevの役割は後で説明します。
ただし、Hookは有効化と信頼確認が前提です。
Jev側は失敗すると元の入力を通すため、この設定だけで全入力への適用を保証するものではありません。

**台本外の技術注記：** 確認対象はリポジトリの`.codex/hooks.json`であり、ユーザー層・システム層を含む実機全体のHook一覧ではない。
設定のmatcherはSessionStartが`^startup$`、PreToolUseが`^Agent$`。
実際のcommandはGitルートを求め、スクリプトのSHA-256を照合してからPythonを実行する。
初回・定義変更後には`/hooks`でproject layerと現在の定義をreview・trustする必要があり、現在の実機で有効・信頼済みかはこの資料更新では未確認。

呼出先の実パスは、起動時が`.agents/skills/github-main-refresh/scripts/refresh_main.py`、入力前処理が`.codex/hooks/jev_preprocess_agent.py`、その先が`scripts/jev/assemble-recipient.mjs`。
SessionStart側はstdinのイベント情報からcwdを使い、status等をadditionalContextで返す。
手動実行では09の`--cwd`を用いる。
Git状態に関する指示の返却と、実行を機械的に停止できることを同一視しない。

Jev側スクリプトはAgent/spawn_agentを受け付けるが、設定上のmatcherと対応する実行経路の確認は別である。
対象はJSONとして読め、family・purpose・required・supplementaryのいずれかを持つ構造化入力。
無効化、対象外入力、assembler不在・失敗・timeout等では入力の差し替えを返さず、元の入力を通す設計である。
これは前処理を強制する安全境界ではなく、失敗時も元入力を保持する入力書換えHook。
資料取得後や親への全入力を、このHook一本ですべて前処理できるとは説明しない。
実APIの利用可否、実際の通過率、受け手での利用は14の別の確認事項とする。

### 11｜一件の依頼は、確認と差し戻しまで回す

**時間：50秒**

**この一枚：** 部品の説明を、一件の仕事の判断・差し戻し・完了へ戻す。

**掲載文言：**

> 依頼と到達点を確認
> 担当が調査・変更・検証
> 必要な別担当レビュー
> 親が根拠を評価し、反映可否を判断
> 許可された反映と、反映後の確認
>
> 足りなければ、親から具体的に差し戻す
>
> 完了報告ではなく、依頼の到達点を満たして完了

**図・配置：** 五段の縦フロー、または二段の横フロー。
親の評価から担当へ戻る線を大きくする。
反映後の確認に不足があれば、親の評価へ戻る線も付ける。
反映の工程は変更・反映まで委任された仕事に限ると示し、調査だけの依頼は依頼された到達点で終える。
反映前の判断を、依頼全体の最終受入と表示しない。
下に「要求・確認結果＝GitHub／変更＝Git」と添える。[^agents] [^roles]

**話す内容：**

ここまでの部品を、一件の仕事の流れに戻します。
親が到達点を確認し、担当が調査、変更、検証を行う。
必要な別担当レビューの結果も、親へ戻します。
足りなければ、何を直して何を再確認するかを具体的に差し戻す。
担当から返答が来たことではなく、依頼の条件と根拠で完了を判断します。
元の権限と範囲内の局所修正は続けますが、新しい費用や権限、範囲変更は私へ戻します。
反映まで任せた仕事は、反映後の実状態を確認してから最終受入します。
これが、モデルとツールの往復とは別の、仕事を完了させるループです。

**台本外の技術注記：** 軽微な依頼へ一律にagent・レビュー・PR・CI・mergeを追加しない。
同じ条件の無断retry、Provider自動切替、自己承認を含めない。
merge判断は親、承認されたheadの操作は許可された担当が行う。
作業の継続・停止・エスカレーションは元の範囲と権限の中で行う。
毎時timerとcodex-ready条件は本編から外す。

> 作業の状態はGit / GitHub

**話す内容：**

仕事のたびに、前に何を決めたか、なぜ別の案をやめたかを説明し直したくありません。
そこで、決定だけでなく理由や制約、訂正と出典を残し、必要な時に引くコンテキスト基盤を置いています。

何でも全部渡すのではなく、今回の依頼に関係する事情を取り出します。
古い記録で、今の指示を上書きするわけではありません。

**台本外の技術注記：** 保存・検索の役割を説明する図であり、全情報源の取込みや全経路の利用が完了したという主張ではない。
過去の文脈を、新しい実行許可や追加要件へ変えない。

### 13｜Jevは、渡す資料を絞る前処理

**時間：40秒**

**この一枚：** 文脈を増やすだけでなく、受け手の前で入力を整える設計を示す。

**掲載文言：**

> Jev：候補の意味判定に使う外部モデル
>
> 資料を取得 → コードで候補を作る
> Jevが選ぶ → assemblerが原文を組み立てる
> 親・担当・次の受け手へ渡す
>
> 必須指示・権限・受入条件は、選別で落とさない

**図・配置：** 入力処理と受け手を上下に分ける。
必須指示等は選別を迂回して受け手へ届く線を描く。
「入力処理の設計」と表示し、全面稼働図に見せない。
10のHookは接続点の一つとして対応させ、すべての取得・引渡しが同じHook経由だとは描かない。[^jev]

**話す内容：**

ただ、文脈を増やしても、毎回全部を大きなモデルに読ませたら負担が増えます。
そこで、コードで候補を作り、意味の選択をJevに任せ、assemblerが原文を組み立てて受け手へ渡す設計にしています。
親だけでなく、資料を取得する担当や、次の担当への引渡しも対象です。
必須の指示や権限、受入条件は選別で落としません。
先ほどのHookは接続点の一つで、全経路をカバーするものではありません。
Jevは監督役ではなく、入力を整える前処理です。

**台本外の技術注記：** 候補選択と、原文を組み立てる処理を分ける。
未評価・不正応答・低確度等で、不確かな入力を勝手に除外しない。
秘密情報の除外、用途ごとの保持・送信条件を守り、失敗を無断の条件緩和や再送で解消しない。
Jev→Luna→Sol→Astraの固定多段処理にしない。
入力選択の信頼度は、正解保証や実行許可ではない。
