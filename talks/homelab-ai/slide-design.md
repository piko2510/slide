# わしの家のAI環境

スライド設計書（v3：現在のCodexハーネス説明版）

副題：AIに任せたくて、作って、壊して、今こうなった

## 発表の目的

社内エンジニアへ、自宅AI環境で何を作り、いまどう運用しているかを説明する。

ただし主題は、独自Harnessをどう開発してきたかではない。

独自Harnessの開発過程は、次の一文で回収する。

> 事故を防ぐために仕組みを足し続けたら、AIを使うための仕組みそのものを自分が保守する状態になった。だから全部捨てて、Codex標準・Git・GitHubへ戻した。

この転換点を置いた後は、現在のCodexハーネスを説明する。

現在のハーネスは、独自runtimeではない。
Codex標準agent、AGENTS.md、Git、GitHub、systemd timer、Context DB、Jev前処理を薄くつないだものとして見せる。

## 話の骨格

1. AIに一件の仕事を任せたかった。
2. 実際には、人間が説明・中継・確認・再開を抱えた。
3. 事故対策を足し続け、独自Harnessが状態機械化した。
4. そのHarnessを捨て、状態の正本をGitとGitHubへ戻した。
5. 今はCodex標準agentとAGENTS.mdを中心に、責務分離で回している。
6. Context DBとJevは判断主体ではなく、受け手へ渡す入力を整える部品である。
7. 作るのは接着剤まで。もう一つの実行基盤は作らない。

## 各スライド

### 01｜わしの家のAI環境

**役割：** 自宅AI環境の紹介として入り、苦悩と現在の設計思想まで話すことを予告する。  
**掲載文言：**

> わしの家のAI環境  
> AIに任せたくて、作って、壊して、今こうなった

**口頭説明：** 家に巨大モデルを置いた話ではない。Codex、クラウドモデル、GitHub、自宅VM、Context DBを使い、一件の仕事をAIへ渡すために何を残し、何を捨てたかの話である。

### 02｜何をAIに任せたかったか

**役割：** 目的を単純な欲望として出す。  
**掲載文言：**

> 「これ直しておいて」で、調査・修正・確認・報告まで進んでほしい  
> 人間は毎回、事情説明と再開係をやりたくない

**口頭説明：** 欲しかったのは完全自律ではなく、日常の開発依頼を到達点まで進めること。Issue、PR、検証、公開確認まで一続きで持っていきたい。

### 03｜任せたはずなのに、自分が忙しい

**役割：** AI利用の現実の重さを出す。  
**掲載文言：**

> 事情を説明する  
> 指示を中継する  
> 結果を読む  
> 止まれば再開する

下部に、

> AIに任せたはずなのに、俺が一番忙しい

**口頭説明：** AIへ渡すたび、会話の前提、前回の判断、どこまで進んだか、何をしてよいかを人間が補う。ここが最初の痛みである。

### 04｜事故を防ぐほど、仕組みが増えた

**役割：** 独自Harness肥大化の理由を一枚で説明する。  
**掲載文言：**

> 二重実行を防ぐ → claim / lease  
> 古いheadを防ぐ → head照合  
> 再開不能を防ぐ → checkpoint / receipt  
> 権限逸脱を防ぐ → gate / authority

下部に、

> 正しい対策を足すほど、自分で管理する状態が増えた

**口頭説明：** 一つ一つの対策は正しい。しかし、それを全部自作した結果、GitHubと独自状態を突き合わせる別の仕事が生まれた。

### 05｜独自Harnessを捨てた

**役割：** 過去話をここで畳む。  
**掲載文言：**

> 375,900 deletions  
> 独自Harnessを撤去し、標準へ戻した

下部に、

> 状態管理はGitとGitHubへ戻す。Codex標準agentを使う。

**口頭説明：** ここから先は開発史を掘らない。重要なのは、独自runtimeや独自状態機械を捨て、標準機能へ戻したこと。

### 06｜ここからは、今のCodexハーネス

**役割：** 現在形へ切り替える。  
**掲載文言：**

> Harnessをなくしたわけではない  
> Harnessの責務を標準機能へ戻した

**口頭説明：** 今のハーネスは、巨大な自作制御基盤ではない。Codex標準agent、AGENTS.md、Git、GitHub、systemd timer、Context DB、Jevを必要最小限で接続している。

### 07｜今の全体像

**役割：** 現在のCodexハーネスを俯瞰する。  
**掲載文言：**

> Owner / Issue  
> 親Astra  
> AGENTS.md  
> Codex標準agent  
> Git / GitHub  
> Context DB / Jev  
> systemd timer

**口頭説明：** 親Astraが判断し、Codex標準agentへ渡し、GitとGitHubで状態を見る。Context DBとJevは入力を整える。systemd timerは毎時の入口であり、独自schedulerではない。

### 08｜状態管理は自作しない

**役割：** 現在の一番大事な設計原則を示す。  
**掲載文言：**

> 作業状態 → Git  
> 要求 → GitHub Issue  
> 変更 → branch / commit / diff  
> 確認 → PR / review / CI  
> 完了 → merge + post-merge verification

下部に、

> 同じ状態を独自ledgerやreceiptへ複製しない

**口頭説明：** 現在のハーネスは、状態の正本を増やさない。GitとGitHubにある状態を、別の状態機械にコピーしない。

### 09｜親Astraと実働サブ

**役割：** モデル配役と責務分離を現在形で説明する。  
**掲載文言：**

> 親Astra：要求・設計・安全境界・受入・merge判断  
> Sol/high：通常worker  
> Luna/max：対象が明確な定型作業  
> Grok：コード実装  
> critic / verifier：read-only確認  
> 子Astra：Solで足りない時だけ振り直し

**口頭説明：** なんでもAstraに投げるのではない。まずSolを標準workerとして使い、Lunaは明確な仕事、Grokはコード実装、critic/verifierはread-only確認に使う。子Astraは固定段階ではなく、親が不足を判断した時だけ使う。

### 10｜AGENTS.mdは実行機ではなく境界線

**役割：** AGENTS.mdの位置づけを誤解なく示す。  
**掲載文言：**

> 誰が判断するか  
> 誰に渡すか  
> どこまで進めるか  
> どこで親へ返すか  
> 何を完了とするか

下部に、

> 実行基盤を自作せず、Codex標準agentへ責務を渡す

**口頭説明：** AGENTS.mdはオーケストレータそのものではない。実行を肩代わりするコードではなく、標準agentを安全に使うための境界線である。

### 11｜Context DBとJevは入力側

**役割：** Context DBとJevを正しい位置に置く。  
**掲載文言：**

> Context DB：事情・理由・制約・訂正を必要時に引く  
> コード：候補を作る  
> Jev：意味関係だけ選ぶ  
> assembler：受け手へ渡す本文を組む

下部に、

> 必須指示・権限・受入条件はJevで選別しない

**口頭説明：** Jevは親でも監督でもない。読む量を減らすための限定前処理で、判断主体は親Astraに残す。

### 12｜Issueからmergeまでの流れ

**役割：** 実際の仕事の流れを一枚で説明する。  
**掲載文言：**

> Issue / 直接依頼  
> 親Astraがscopeと受入条件を決める  
> Context / Jevで入力を整える  
> workerが隔離worktreeで実行  
> test / review  
> 親Astraが受入  
> merge  
> post-merge verification

**口頭説明：** 直接依頼なら、明示された終了点まで。Issueなら`codex-ready`の条件を見る。merge前後の確認まで含めて、現在のハーネスのライフサイクルになる。

### 13｜今の設計思想

**役割：** 発表を現在の思想で締める。  
**掲載文言：**

> 作るのは接着剤まで  
> もう一つの状態機械は作らない

下部に、

> Codex標準、Git、GitHub、AGENTS.md、Context/Jevを薄くつなぐ

**口頭説明：** 完成したという話ではない。Jevの噛み合わせ、配役、Contextの渡し方はまだ調整中。ただし、問題が起きたときに「何を足すか」だけでなく「何を作らないか」を先に見るようになった。ここが一番大きい変化である。
