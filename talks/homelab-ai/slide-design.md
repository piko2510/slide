# AIに任せるために、何を作らないか

スライド設計書（2026年9月25日）

副題：自宅AI環境を作り直して分かった、Harness・モデル・文脈の責務分離

## 1. 発表の目的

発表者が自宅でAI環境を作り直してきた経験から、**AIに仕事を任せるために、どの責任を自分で持ち、どれを既存の仕組みへ戻したか**を伝える。

対象は社内のエンジニア。発表10分、質疑5分。開催日は未定。

中心となる主張は次の一文とする。

> AIへ任せる範囲を広げるには、管理機構を増やすだけでなく、判断と状態をどこが持つかを選び直す必要があった。

旧Harness、モデル配役、Context DB、Jevを、それぞれ独立した技術紹介にしない。「困ったこと → 試したこと → 新しく生じた負担 → 選び直した責任」という因果でつなぐ。

## 2. 構成方針

現行の13枚構成を維持し、次の点を補強する。

- 旧Harnessの機構は、防ぎたかった事故と対応させる。
- 撤去後も、規則の保守や必要な検証は残ったことを示す。
- モデル配役は、判断の種類、照合可能性、必要な能力で説明する。
- Context DBは、情報量の問題より先に「判断理由を残す必要」を説明する。
- Jevの失敗は、入力不足、分割方法、失敗時の処理を分けて示す。
- 現在構成は責務の整理として説明し、性能改善や完全自律の達成とは区別する。

一連の出来事を、すべて順番に解決したようには描かない。Context DBなど並行して進めた取り組みは、発表上の説明順であることが分かる接続にする。

## 3. 共通デザイン

| 項目 | 指定 |
|---|---|
| 画面 | 16:9、白背景 |
| フォント | Meiryo UI |
| 文字色 | 本文 `#222222`、補足 `#505050` |
| 強調色 | 青 `#1F5FAF` |
| 補助色 | 枠線 `#D0D5DD`、面 `#F5F6F8` |
| 文字サイズ | 表紙40〜44pt、見出し32pt、本文20〜23pt、注記14〜16pt |
| 図 | 編集可能な図形とコネクタ |
| 情報量 | 1枚につき主張1つ、主図1つ |
| ページ番号 | `NN / 13` |

スライドには短い掲載文言と主図を置く。経緯や留保は口頭説明で補う。ただし、数値の単位や「未測定」はスライドにも残す。

矢印は、因果、入力の流れ、担当への割当を示す場合だけ使う。製品名の羅列を矢印で結ばない。

## 4. 各スライドの設計

### 01｜AIに任せるために、何を作らないか

**役割：** 発表全体の問いを示す。\
**時間：** 20秒

**掲載文言**

> AIに任せるために、何を作らないか\
> 自宅AI環境を作り直して分かった、Harness・モデル・文脈の責務分離

下部に小さく：

> 任せる仕組みを作ったら、その仕組みの管理が仕事になった。

**図と配置**

タイトルを左寄せで大きく配置する。詳細な構成図は置かず、下部に「人間 → 管理の仕組み → AI」の小さな概念図を添える。

**口頭で補うこと**

自宅のProxmox上に作業環境や情報基盤を置き、クラウドのAIモデルと組み合わせている。その環境を作る途中で、何度も責任の分け方を変更した話だと伝える。

**次への接続**

> 最初に減らしたかったのは、AIを動かすために自分がやっていた段取りでした。

### 02｜AIを使うほど、自分の段取りが増えた

**役割：** 解決したかった具体的な負担を共有する。\
**時間：** 40秒

**掲載文言**

> 事情を説明する → 担当を選ぶ → 指示を渡す\
> 結果を読む → 次へ渡す → 止まったら再開させる

下部：

> 任せたかったのに、自分が工程をつないでいた。

**図と配置**

横方向の作業フロー。工程の間に「自分」の小さなラベルを繰り返し置き、人間が中継している位置を示す。

**口頭で補うこと**

回答を得ることと、一件の仕事を到達点まで任せることは違った。必要な人間判断は残しつつ、通常の調査や局所修正のたびに呼び戻される状態を減らしたかった。

**次への接続**

> この段取りをコードへ移せば、任せられると思いました。

### 03｜事故を防ぐため、管理機構を足した

**役割：** 旧Harnessを作った合理的な理由を説明する。\
**時間：** 45秒

**掲載文言**

| 防ぎたかったこと | 追加した仕組み |
|---|---|
| 同じ処理の二重実行 | claim / lease |
| 許可範囲を越えた操作 | Authority / gate |
| 中断後の誤った再開 | checkpoint / receipt |
| 古い変更へのレビュー | 対象headの照合 |

下部：

> 一つずつ、追加する理由があった。

**図と配置**

中央に「独自Harness」。周囲に上記4組を置く。機構名より、防ぎたかった事故を大きく表示する。

**口頭で補うこと**

Harnessは、AIに指示を渡し、道具の使用や作業の進行を支える仕組み。旧設計では、人間の中継を減らすため、実行許可、状態、復旧まで自前で扱おうとした。

**次への接続**

> ところが、機構を増やすほど、それらの整合性を守る仕事が増えました。

### 04｜仕事を進める前に、管理状態の確認が増えた

**役割：** 肥大化を機能数ではなく、作業への影響で示す。\
**時間：** 45秒

**掲載文言**

上段：

> 本来の仕事：指摘を直す → 検証する

下段：

> Authorityの継続条件を確認\
> → 作業状態を照合\
> → reviewの再実行条件を確認\
> → 本来の修正へ戻る

下部：

> 作業を管理する仕組みが、もう一つの保守対象になった。

**図と配置**

本来の短い経路と、管理処理へ迂回する経路を上下で対比する。下段は記録にある事象を説明用に簡略化した図とする。

**口頭で補うこと**

必要な安全確認そのものが問題だったわけではない。GitやGitHubの状態に加えて独自の管理状態を持ち、その対応関係まで維持する責任が増えていた。

**次への接続**

> そこで個々の機構を直し続けるより、自分で持つ責任を減らす方向へ切り替えました。

### 05｜独自Harnessを撤去し、標準機能へ戻した

**役割：** 発表前半の転換点。\
**時間：** 50秒

**掲載文言**

> 375,900 deletions\
> 300 files changed / 629 additions

責務の移動：

| 責任 | 移した先 |
|---|---|
| 実行ループ | Codex |
| branch / commit / diff / worktree | Git |
| Issue / PR / review / CI / merge状態 | GitHub |
| 必要な接続と入力加工 | 自作部分として残す |

注記：

> 撤去commitのGitHub差分。手書きコード量や性能改善率ではない。

**図と配置**

左に多くの責任を抱えた旧Harness。右に責務別の移管先。数値は上部に置き、責務の移動を主図にする。

**口頭で補うこと**

外部Providerの呼出し口や必要な安全境界、レビュー、検証は残した。現在も役割があるものまで一括で消したわけではない。

**次への接続**

> ただ、コードを削っても、判断しなければならないことは残りました。

### 06｜コードを減らすと、今度は規則が増えた

**役割：** 撤去を成功物語だけで終わらせない。\
**時間：** 40秒

**掲載文言**

> 独自コードを撤去\
> → 判断や境界をAGENTS.mdへ\
> → 重複する規則と説明が増加

数値：

> 21,344 bytes → 39,242 bytes\
> 整理Issue起票時の、1週間前との比較

下部：

> 規則も、読み解き、更新する必要がある。

**図と配置**

コードから文書へ責任が移る図。右側にファイル量の増加を示す。単位は必ずbytesとする。

**口頭で補うこと**

この数値は当時のUTF-8ファイル量であり、現在のサイズや消費トークンではない。意味や権限境界を維持しながら重複を削り、別の台帳や新しい機構へ移すだけの整理は避けようとした。

**次への接続**

> その規則を読み、判断を引き受けるモデルの側にも、仕事を集めすぎていました。

### 07｜Astraへ広く任せても、往復は残った

**役割：** モデル配役を見直した理由を示す。\
**時間：** 40秒

**掲載文言**

左側：

> 期待\
> 広い文脈を理解して、判断と進行を任せたい

右側：

> 運用で起きたこと\
> 意図の深読み\
> 依頼していない完了条件\
> 追加調査と不要な往復

下部：

> どこまで考えてもらうかも、設計する必要があった。

**図と配置**

「期待した役割」と「実際に広がった仕事」の対比。モデルの性能順位や優劣は描かない。

**口頭で補うこと**

ここで述べるのは自分の運用での経験であり、モデル一般の性能評価ではない。能力だけでなく、与える範囲と終了点の決め方も見直した。

**次への接続**

> そこで、判断の種類と結果の確かめ方に合わせて、仕事を分け直しました。

### 08｜判断の種類と照合可能性で、担当を分ける

**役割：** 現在の配役と委任単位を説明する。\
**時間：** 55秒

**掲載文言**

| 担当 | 主な責任 |
|---|---|
| 親Astra | 要求、範囲、安全境界、直接割当、最終受入 |
| Sol | 通常の調査、実行、検証 |
| Luna | 対象と終了点が明確で、結果を照合できる作業 |
| Grokなど外部担当 | 通常のコード実装など |
| 子Astra | 具体的な能力不足を親が確認した場合の担当 |

下部：

> 一件を到達点まで委任する。局所修正のたびに中継しない。

**図と配置**

親Astraから各担当へ直接割当線を引く。子Astraの線には「必要時のみ」と記す。LunaからSol、Astraへ順番に上がる階段は描かない。

**口頭で補うこと**

失敗時は、資料不足、認証、権限、外部障害とモデルの能力不足を分ける。同じ担当が許可範囲内で修正できるものは、検証まで続ける。

**次への接続**

> 担当を分けても、その担当へ事情を渡す問題は残ります。ここで、並行して作ってきたContext DBの話につながります。

### 09｜事情を残すだけでは、必要な文脈は渡せなかった

**役割：** Context DBの目的と、次に生じた問題を一枚でつなぐ。\
**時間：** 50秒

**掲載文言**

左側：

> Context DBに残したいもの\
> 結論／理由／制約／時点／出典／訂正

中央：

> 検索して参考情報を集める

右側：

> 本題の前に\
> 「今回必要なのはどれか」を読む

下部：

> 保存することに加えて、何を渡すかを考える必要があった。

**図と配置**

左にContext DB、中央に複数の資料、右に受け手のモデル。資料からモデルへ入る手前に「選ぶ仕事」を明示する。

**口頭で補うこと**

結論だけを残すと、後からその適用範囲や訂正を判断しにくい。一方、背景を多く残せば、受け手が選別する仕事も生じる。過去の記録は判断材料であり、現在の操作許可にはならない。

**次への接続**

> この選別のうち、範囲を狭く定義できる意味判断を、前処理へ移そうとしました。

### 10｜Jevへ、限定した意味判断を切り出した

**役割：** 導入した製品ではなく、移した仕事を説明する。\
**時間：** 45秒

**掲載文言**

> 取得\
> → コードで候補を作る\
> → Jevが限定的な意味関係を判定\
> → コードで入力を組み立てる\
> → 受け手が本題を進める

補足：

> 例：参考資料が今回の目的に関係するか

下部：

> 狙いは、後段が読む仕事を減らすこと。正味効果は未測定。

**図と配置**

入力の受け渡し部分を拡大したフロー図。Jevだけを大きくせず、コードによる候補化と結果の扱いも同じ大きさで描く。

図の上に「既存の受け渡し箇所で使う前処理」と記す。

**口頭で補うこと**

システム全体を最初に一度だけJevへ通す構造ではない。資料返却や担当への入力など、既存の受け渡し境界で使う。Jevが担当への操作許可や最終受入を決めることはない。

**次への接続**

> ただ、選別を入れれば必要なものだけ残る、というほど簡単ではありませんでした。

### 11｜Jevの失敗から、選別する範囲を狭めた

**役割：** 実際の失敗と現在の境界を結び付ける。\
**時間：** 65秒

**掲載文言**

左側：

| 起きた問題 | 見直した対象 |
|---|---|
| 対応不要と誤判定 | 質問と判断材料 |
| plain textだけでは不足 | HTMLを含む入力 |
| 段落分割で候補が競合 | 情報をまとめる単位 |
| 代替処理で制約が欠落 | 失敗時に保持する入力 |

右側：

```text
必須指示・権限・受入条件
        └─ 選別せず保持 ─────────┐
                               ├─ 入力組立
参考資料 ─ Jevによる限定選別 ────┘
```

下部：

> 未評価や失敗を「不要」と扱わない。

**図と配置**

左35％に失敗と見直し対象、右65％に二つの入力経路。必須情報からJevへは線を引かない。

**口頭で補うこと**

誤判定をすべてモデルの能力不足と考えると、入力不足やプログラム側の欠落を見逃す。不確実な制約や反証は後段へ残す。また、worker単体の消費だけでは、親側の負担や往復を含む全体効果を評価できなかった。

**次への接続**

> こうした変更を重ねて、今はそれぞれが持つ責任をこのように分けています。

### 12｜現在は、責任をこのように分けている

**役割：** ここまでの経緯を、現在の自宅AI環境へ結び付ける。\
**時間：** 65秒

**掲載文言**

| 領域 | 責任の置き場所 |
|---|---|
| 実行と状態 | Codex：実行ループ／Git：変更／GitHub：要求と開発状態 |
| 判断と実働 | 親Astra：範囲と受入／Sol・Luna・外部担当：割り当てた仕事 |
| 文脈と前処理 | Context DB：事情と根拠／Jev：限定的な意味判定 |
| 共通規則 | AGENTS.md：委任、継続、停止、安全境界 |

下部：

> どれか一つに、すべての責任を集めない。

**図と配置**

「実行と状態」「判断と実働」「文脈と前処理」の三領域を並べ、AGENTS.mdを共通規則として添える。

下端に実行場所の帯を置く。

- 自宅Proxmox／VM：作業環境と情報基盤
- クラウドサービス：モデル推論、GitHubなど

これは責務図であり、通信経路を網羅する構成図にはしない。クラウドモデルを自宅VM内に配置しない。

**口頭で補うこと**

自作部分には接続、入力加工、必要な安全境界が残る。その保守は必要だが、独自の作業状態やライフサイクルを再び抱え込まないことを意識している。現在も調整中の構成である。

**次への接続**

> 振り返ると、一貫していた目的は、自分がAIの段取り係にならないことでした。

### 13｜任せるために、自分で持つ責任を選ぶ

**役割：** 聴衆が持ち帰る設計上の問いを残す。\
**時間：** 40秒

**掲載文言**

中央：

> AIに仕事を任せるために、管理システムを作りすぎた。\
> だから今は「何を自分で持たないか」を設計している。

下部の三点：

1. 標準機能が持つ状態を、別に持たない。
2. 判断の範囲と、結果を確かめる方法を決める。
3. 文脈を選別しても、指示・権限・受入条件は落とさない。

**図と配置**

中央メッセージを大きく置き、下部に三点を並べる。新しい構成図や技術名を追加しない。

**口頭で補うこと**

複雑さをなくせたわけではない。どこが引き受けるかを選び直している。Jevを含む正味の効果は、親子全体の費用、時間、往復、人間介入を含めて評価する必要が残っている。

## 5. 時間配分

| 範囲 | 内容 | 時間 |
|---|---|---:|
| 01〜02 | 発表の問いと人間の段取り | 1分00秒 |
| 03〜05 | 旧Harnessの追加、肥大化、撤去 | 2分20秒 |
| 06〜08 | 規則とモデル配役の見直し | 2分15秒 |
| 09〜11 | Context DBとJevの導入、失敗 | 2分40秒 |
| 12〜13 | 現在の責務分離と持ち帰り | 1分45秒 |
| 合計 | 本編 | **10分00秒** |

## 6. 事実と表現の境界

- 削除量はGitHub差分として扱う。開発量、削減効果、生産性へ換算しない。
- AGENTS.mdのサイズは当時の比較値。現在値や消費トークンとして扱わない。
- モデル配役は、この環境での運用方針。一般的な性能順位として示さない。
- Jevの前処理は導入の狙いと設計を説明する。高速化や費用削減の達成を断定しない。
- Gmailの例は処理上の問題だけを説明し、実メールや個人情報を載せない。
- 図には、非公開URL、内部IP、VM番号、認証情報を載せない。
- 未測定の効果を示す棒グラフや、実測に見える架空の成功例は作らない。
