# 発表全体の文脈 v3.1

## タイトル
**AIに任せるために、何を作らないか**

### サブタイトル
自宅AI環境を作り直して分かった、Harness・モデル・文脈の責務分離

## 発表条件
- 対象：社内エンジニア
- 本編：13枚
- 発表：10分
- 質疑：5分

## この発表の中心
これは「便利なAIサービスを並べた構成紹介」ではない。

AIへ仕事を任せようとして管理機構を作りすぎ、その管理機構まで自分の仕事になった結果、
**何を捨て、何を標準へ戻し、どの判断だけを残したか**を話す。

最初の問題はモデル性能ではなかった。

```text
事情を説明する
→ モデルを選ぶ
→ 指示を中継する
→ 結果を読む
→ 次の担当へ渡す
→ 止まったら再開させる
→ 本当に終わったか確認する
```

AIを使うほど、人間がオーケストレーターになっていた。

## 第1の反応：Harnessへ全部寄せる
重複実行、権限逸脱、古いhead、response loss、retry、review、CI、復旧を安全に扱うため、
Router、state、gate、claim/lease、checkpoint、receipt、handoffなどを積み上げた。
個々の機構には理由があった。

しかし、やがて仕事本体より **Harnessを成立させるための仕事** が増えた。

2026-09-04の旧Atem Harness撤去commitのGitHub差分：
- 300 files changed
- 375,900 deletions
- 629 additions

これはGitHub差分上のdeletionsであり、純粋な手書きLOCや性能改善率ではない。

## 第2の反応：標準へ戻す
- 実行ループ：Codex
- branch / commit / diff / worktree：Git
- Issue / PR / review / CI / merge状態：GitHub
- 自作コード：外部接続、入力加工、権限境界など必要な接続部分

ただし複雑さは消えなかった。
整理Issue起点ではAGENTS.mdが一週間で **21,344 bytes → 39,242 bytes**。
これはUTF-8ファイル量であり、実消費トークンではない。

```text
独自コードが太る
→ 削る
→ 規則へ寄せる
→ 規則が太る
```

## 第3の反応：強いモデルへ寄せすぎない
Astraへ広い文脈と判断を集めるほど、深読み、独自の完了条件、追加調査、消費、不要な往復が増えることがあった。

現在はモデルの序列ではなく **判断の種類** で分ける。

- 親Astra：目的、範囲、安全境界、直接割当、結果評価、最終受入
- Sol：通常の実働。迷う仕事もまずここ
- Luna：対象、操作、終了点が明確で、結果を照合できる仕事
- Grok等：通常のコード実装など専門作業
- 子Astra：環境不備ではなく、具体的な解釈・判断・実行品質不足が確認された場合だけ

固定の `Luna → Sol → Astra` 昇格ルートではない。

## 第4の問題：文脈を全部LLMに読ませる
Context DBへ事情・判断理由・制約・時点・出典を残すほど、
今度は「今回どの情報が必要かを選ぶ」こと自体がLLMの仕事になる。

そこでJevを導入した。
目的はAIを増やすことではなく、**生成モデルでなくてもよい限定判断をLLMから剥がすこと**。

```text
取得
→ コードで候補化
→ Jevで限定的な意味判定
→ コードで入力を組み立て
→ LLMは本題を考える
```

## Jevも一発では完成しなかった
実メール調整や接続では、
- 対応不要の誤判定
- plain textだけでは判断材料不足
- HTML側に必要情報があるケース
- 段落分割による候補競合
- 依存不足時のfallbackで重要制約を落とす問題
が出た。

現在は、
```text
必須指示 ───────────────┐
権限 ──────────────────┤
受入条件 ──────────────┤
                        ↓
                     入力組立
                        ↑
参考資料 → Jevで限定選別 ─┘
```

とし、必須指示・権限・受入条件をJevの選別対象にしない。

## 13枚
1. AIに任せるために、何を作らないか
2. AIを使うほど、なぜか自分の仕事が増えた
3. ならば、Harnessに全部管理させればいい
4. 安全にするほど、Harness自身が仕事になった
5. 37万5900行消して、標準機能へ戻った
6. ただし、複雑さは消えない。場所が変わる
7. 一番賢いモデルに全部考えさせるのも違った
8. 仕事の難しさではなく、判断の種類で分ける
9. それでも残った「全部読ませる」問題
10. JevはAIを増やすためではなく、AIの仕事を減らすため
11. そしてJevにも、選ばせてはいけないものがあった
12. 今の構成は「シンプル」ではなく「責任の置き場所が明確」
13. AIの段取り係にならないために、Harness自身も管理しない

## 守る境界
- 旧Harnessを無駄だったで済ませない。個々の機構には理由があった。
- 37万5900行はGitHub差分のdeletions。
- Astra / Sol / Lunaを一般性能ランキングとして語らない。
- Jevの全体効果はまだ定量確定していない。
- 現在の構成を「完成」「完全自律」と断定しない。
- 最終結論は、複雑さをゼロにしたことではなく **複雑さと判断の置き場所を選び直したこと**。
